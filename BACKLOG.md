| B-P0-4 | MFA/2FA for staff accounts | ✅ | TOTP (RFC 6238, via `otplib`) shipped in `src/auth/mfa/`: `POST /auth/mfa/setup` → `enable` → login returns a challenge → `POST /auth/mfa/verify`, plus 10 single-use recovery codes and a `disable` that requires the password **and** a code. Secrets are stored only as AES-256-GCM envelopes keyed by `MFA_TOTP_KEY` (mirrors the WhatsApp vault; absent key ⇒ clear 503, not a boot failure). Schema added via Prisma-generated migration `20260923020000_add_user_mfa`, verified with `migrate diff` to leave zero residual drift. Covered by `test/auth-mfa.e2e-spec.ts` (17) and `src/auth/mfa/mfa-secret.vault.spec.ts` (14), which pin the properties that make it real rather than decorative: password alone yields no session **and no refresh cookie**; the `mfa`-typed challenge token is refused as a bearer credential (the bypass that would collapse the whole factor); codes can't be replayed inside their own 30s step; recovery codes are single-use; wrong codes burn the same lockout budget as wrong passwords; and a merely *pending* enrolment never gates login. Reasoning recorded as `ARCHITECTURE_DECISIONS.md` AI-19. Suite after: 32 e2e suites / 290 passed, 18 unit suites / 96 passed. **Enrolment is opt-in per user — nothing yet requires privileged roles to use it (B-P0-10), and there is no frontend yet (F-P0-4).** |
| B-P0-10 | Decide and enforce an MFA policy for privileged roles | ✅ | Done (ADR **AI-20**). `Organization.mfaPolicy` (`OPTIONAL` → default, so no existing tenant changes) + `mfaGraceUntil`, as typed columns. Enforcement covers `ORG_OWNER`/`ORG_ADMIN`/`ACCOUNTANT` and **never refuses the login** — it issues a session that `MfaEnrolmentGuard` (global, deny-by-default, registered before `PermissionsGuard`) confines to `/auth/me`, `/auth/logout-all` and the three enrolment routes. Refusing instead would be a permanent lockout, since enrolling needs a session. The flag is recomputed per request in `JwtStrategy` (policy columns joined into the lookup it already does), so enrolling lifts the restriction on the next call with no token rotation. Switching the policy on without a date grants 14 days’ grace; during it the user keeps a full session and is warned via `mfaEnrolment: { state, deadline }` on both the login response and `/auth/me`. `GET /auth/mfa/policy/report` (gated on `organizations.update`, not `users.read` — it names unprotected accounts) drives the decision. 17 e2e tests; the guard, the grace window and the role filter were each broken in turn to confirm the suite detects them. |
| B-P0-13 | `Branch.deviceKey` is one plaintext secret shared by every scanner on a branch | ⬜ | Found doing B-P0-5. `KioskDevice` stores a per-device sha256 hash and can be revoked one device at a time (`active = false`); `Branch.deviceKey` is a single **plaintext** column, shared by every scanner at that branch, and the only way to revoke one compromised scanner is to re-key all of them. The branches UI already exposes rotate-and-copy for it. Move `/devices/check-in` onto the `KioskDevice` registry (it is already the canonical device table now that `Attendance.deviceId` points at it), migrate existing branch keys into it as one device per branch, then drop the column. |
| B-P0-14 | Five unnamed throttler configs capped every endpoint at ~4 requests/minute | ✅ | Found while running the app to screenshot the UI redesign. `ThrottlerModule.forRoot([...])` listed five configs — 120 general, 20 auth, 30 analytics, 40 members, 50 billing — reading as if each applied to its own area. `@nestjs/throttler` names every config without an explicit `name` `'default'` (`throttler.guard.js`), so all five collided on one counter **and each incremented it**: one HTTP request counted as five hits against the strictest limit. Measured against the running API, the **fifth** request from an address was refused, so the advertised 120/min was really ~4/min and a single page load exceeded it — every real user would have seen 429s within seconds. Every analytics/members/billing/auth controller already carries its own `@Throttle` with exactly the numbers that list was reaching for, so the fix is one unnamed entry at 120/min. Re-measured after the fix: `/health` (its own `@Throttle(20)`) refuses at #21, `/organizations/current` (no decorator) at #121 — both exactly as documented. Config extracted to `common/rate-limit/throttler.config.ts` with a unit test that fails if a second entry is ever added, since the failure mode is silent. |

## Process fix (applies to every item above)

PR** that ships a module, not in a later catch-up pass — the ~5-week documentation gap this audit
found (Aug 22 → Sep 23 undocumented) is what made B-P0-1 through B-P0-3 invisible until now.
