| B-P0-7 | Every `@IsBoolean()` DTO field silently coerces strings to `true` | 🚧 | Found while writing B-P0-2's notification tests, **confirmed empirically**: `main.ts` sets `transformOptions: { enableImplicitConversion: true }`, whose boolean conversion is `Boolean(value)` — so `{"inApp": "false"}` and `{"inApp": "0"}` both arrive as `true`, and `@IsBoolean()` never sees a value it could reject. A client opting *out* of a notification category was therefore silently opted *in*. Exactly the bug class `ARCHITECTURE_DECISIONS.md` AI-7 already fixed once for `SMTP_SECURE`. **Fixed for the 5 fields in `update-notification-preferences.dto.ts`** (a `RawBoolean()` transform passes the untouched value through so `@IsBoolean()` is the real gate), covered by a regression test asserting `"false"`/`"0"`/`"nope"` all 400. **18 `@IsBoolean()` fields across 16 other DTOs still have the hole** (`create-user.dto.ts` `isTrainer`, `create-invoice.dto.ts`, `list-invoices-query.dto.ts`, …). Deliberately not swept in a test-coverage change: the clean fix is either the same decorator applied field-by-field (each needing its own test) or dropping `enableImplicitConversion` globally, which would change number coercion on every query DTO and needs its own verification pass. Pick one and finish it. |
| B-P0-8 | Group training tables are raw-SQL with no Prisma model | ⬜ | Same class as B-P0-1, different module: `src/classes/classes.service.ts` reads and writes `class_programs`/`class_sessions`/`class_bookings` entirely through `$queryRawUnsafe`, and none of the three has a `model` block in `schema.prisma`. Port it the same way B-P0-1 did, and verify with `prisma migrate diff` against a migrated database that the modelled FK constraints match the physical ones. |
